# ユーザー画像のファイル名変更：参照更新の調査と見積もり

調査日: 2026-10-17

追記: 以下は実装前の見積もり記録。現在はファイル名変更、参照更新、編集中データの同期、履歴再構築、失敗時の巻き戻しと起動時回復まで実装済み。現在の仕様は [image-rename.md](image-rename.md) を参照。

## 前提と今回追加した関数

画像の保存ファイル名を変更し、利用箇所も新しいパスに追従させる。対象はユーザー画像で、プリセットと画像形式の変更は対象外。画像の参照方式は現在のファイルパスを維持する。

バックエンドに `plan_user_image_rename` コマンドを追加した。引数は `imgName` と拡張子を含む `newName`。既存ファイルや参照先の書き換えを行わず、変更前後のパス、保存済み参照のファイルとJSON位置、走査件数、走査できなかった項目を返す。ソースは `src-tauri/src/file_ops/image_rename.rs`、入口は `image_manager.rs`。

新しい名前の禁止文字・予約名・長さ、元画像の存在、拡張子維持、変更先の衝突を検証する。旧 `BgImage/user` パスとWindowsの区切り文字・大文字小文字の差も検出対象に含める。任意の文章中に書かれたパス文字列は画像参照として扱わない。

このコマンドは実行計画の調査用であり、リネーム実行機能ではない。保存済み参照が0件でも、未保存の編集中データに参照がないことは保証できない。そのため `requires_runtime_sync` を返し、`issues` がある場合も参照更新の対象が確定したものとして扱わない。画面への接続と実際のリネーム・参照更新は今回の見積もり対象。

## 保存されている参照

| 場所 | フィールド・構造 | 改修が必要な理由 |
| --- | --- | --- |
| `settings.json` | `bgimage.path` | アプリ背景。Tauri Storeのキャッシュとフロントの設定値も同期する |
| `TypeNap_Library/<作品>/story_metadata.json` | `cover` | 画像を使った作品表紙。色指定は変更しない |
| Character / World / Entity のJSON | `imagePaths[]` | 3種類は共通の画像参照形式なので、共通処理にできる |
| `Backup/Alive` | `backups[].base_content` 内のJSONと `json_patch` の値 | 現在の文書だけ更新すると、履歴復元で旧パスが復活する |
| `Backup/Necropolis` | 削除済み資料のJSONスナップショット、旧バックアップ | 削除済み資料の復元後も画像を表示するため |

Aliveは単純なJSON文書の集まりではなく、JSON文字列で保存した基準文書とRFC 6902の差分を持つ。無差別な文字列置換ではなく、基準文書と差分を整合した形で変換する必要がある。今回の調査関数は既知の画像フィールドと差分の値を検出する段階までで、履歴の書き換え・再生検証は行わない。

## メモリ上の参照と保存競合

- `imageStore`: 一覧、旧パスから新パスへの差し替え。
- `fileStore.storyList` / `storyStore.workspaces`: 表紙と、開いた作品の表示。
- `txtStore.workspaces`: JSON文字列内の `imagePaths`。未保存の変更を保持して差し替える必要がある。単純な再読み込みは編集を失わせる。
- `txtStore` の保存キュー: 実行中・待機中の保存が旧パスを書き戻さないよう、名前変更操作との順序を決める。
- 設定画面の `selectedBgImage`、作品表紙の `editedCoverColor`、`ObjectImagesDialog` 内の画像選択ドラフト。
- ImageFixedViewのプレビュー、選択パス、寸法キャッシュ。

写真表示部品は受け取ったパスを表示するため、通常は個別の改修をせずにストアの同期で追従できる。タブや資料のUUIDは変更しない。現時点の画像参照は画像UUIDではなくパスなので、資料UUIDの仕組みだけではこの問題は解決しない。

## 実装案

1. 名前と参照対象を検証し、走査失敗があれば変更を中止する。
2. フロントの保存キューと画像関連の書き込みを調整し、未保存ドラフトも含めて旧パスから新パスへの変更を準備する。
3. 画像の移動と参照ファイルの更新を一つの操作として扱う。既存の `atomic_file` は1ファイルの更新用なので、複数ファイルの処理には作業記録とロールバック・起動時回復を追加する。
4. 設定はTauri Store経由でもキャッシュを同期する。ファイルを直接書き換えるだけにしない。
5. バックアップの基準文書・差分と削除済みスナップショットを更新し、履歴を再生して整合性を検証する。
6. 成功後にストアと画面上のドラフトを同期し、一覧の選択・並び順・プレビューを更新する。

`CONTENT_WRITE_LOCK` はJSON保存やバックアップの排他に再利用できる。ただし画像の追加・削除、表紙更新、設定保存など、現状で同じロックを使っていない処理もあるため、既存ロック一つだけで全体が安全になるわけではない。

## 改修規模の目安

現行形式を維持し、保存済みデータ・未保存編集・履歴復元・途中失敗からの回復を含める場合の概算。

| 作業 | 作業時間の目安 |
| --- | --- |
| ファイル名変更、保存済み参照の更新、書き込みの排他調整 | 5〜8時間 |
| バックアップと削除済み資料への追従、履歴の再生検証 | 4〜7時間 |
| メモリ上のストア・ドラフトと保存キューの同期 | 4〜7時間 |
| FixedViewの名前変更UI、入力エラー、翻訳 | 2〜4時間 |
| 作業記録・ロールバック・起動時回復と統合テスト | 8〜14時間 |
| 合計 | 23〜40時間程度、約3〜5人日 |

本体は約15〜20ファイル、これにテストの追加・更新が必要な中規模改修。今回の事前調査関数は含むが、実行処理の試作はまだしていないため、これは確約ではなく現行コードの静的調査に基づく見積もり。

単純なファイル名変更と画面の名前変更ダイアログだけなら小規模だが、既存の画像利用先を保つ要件は満たせない。工程を縮める場合も、何を追従対象から外すかを明示する必要がある。

## 必要な検証

名前の衝突、禁止名、拡張子、同名・大文字小文字だけの変更、背景・表紙・3種類のJSON、複数作品からの共有、未保存編集、保存中の実行、確認後に参照が増えた場合、バックアップ全世代の再生、削除済み資料の復元、途中の書き込み失敗、アプリ強制終了後の回復、プリセット保護を確認する。
